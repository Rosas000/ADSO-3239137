# ADR-002 — Resolución de concurrencia en el descuento de inventario

- Estado: Aceptada
- Fecha: 2026-11-13
- Decisores: aprendiz A14
- Relaciona: architecture.md sección 6, RN01, RN03, RN04, RNF01

---

## Contexto

El acta describe el escenario: dos asesores intentan alquilar la última unidad
disponible del mismo artículo al mismo tiempo. El sistema debe garantizar que
una petición tiene éxito y la otra recibe 409 Conflict, y que el inventario
nunca queda negativo.

Existen dos condiciones de carrera distintas, no una:

1. Sobre el inventario del artículo: dos peticiones que descuentan la misma fila.
2. Sobre el límite del organizador (RN01): dos peticiones del mismo organizador
   que leen el mismo contador de unidades pendientes y ambas lo superan.

Bloquear solo los artículos resuelve la primera pero no la segunda, porque el
contador de pendientes vive en rentals y rental_lines, no en articles.

---

## Decisión

Usar bloqueo pesimista de fila dentro de una transacción, en dos niveles:

1. Bloquear la fila del organizador al inicio, para serializar sus peticiones.
2. Bloquear las filas de los artículos en orden ascendente por id.

Implementación en RentalService:

    DB::transaction(function () use ($lines, $organizerId, $advisorId) {
        // 1. Bloquear el organizador serializa SUS peticiones concurrentes.
        //    Sin esto, dos peticiones del mismo organizador leerían los mismos
        //    pendientes y ambas pasarían RN01.
        $organizer = Organizer::where('id', $organizerId)
            ->lockForUpdate()
            ->first();

        // 2. RN03 y RN01 leen bajo el bloqueo del organizador.
        $this->assertOrganizerNotBlocked($organizer);
        $this->assertOrganizerWithinLimit($organizer, $lines);

        // 3. withTrashed distingue "no existe" (validado en la forma) de
        //    "existe pero dado de baja" (regla de negocio, 422).
        //    Sin withTrashed, SoftDeletes excluiría los dados de baja y el
        //    422 de baja lógica nunca se produciría.
        $articles = Article::withTrashed()
            ->whereIn('id', collect($lines)->pluck('article_id'))
            ->orderBy('id')
            ->lockForUpdate()
            ->get()
            ->keyBy('id');

        // 4. Procesar en el mismo orden ascendente.
        foreach (collect($lines)->sortBy('article_id') as $line) {
            $article = $articles->get($line['article_id']);
            if ($article === null || $article->deleted_at !== null) {
                throw new ArticleUnavailableException();
            }
            if ($article->available_units < $line['quantity']) {
                throw new InsufficientUnitsException();
            }
            $article->decrement('available_units', $line['quantity']);
            // crear RentalLine con article_reference y article_name congelados
        }
    });

---

## Por qué orderBy('id') es obligatorio

PostgreSQL adquiere los bloqueos FOR UPDATE en el orden en que el plan de
ejecución recorre las filas, no en el orden de la lista de ids que se pasa a
whereIn. Un sortBy sobre la colección PHP ocurre después de adquirir los
bloqueos, por lo que no influye en el orden de adquisición.

orderBy('id') hace que el nodo de ordenamiento del plan ordene antes del
FOR UPDATE, de modo que dos peticiones que tocan los mismos artículos los
bloquean en el mismo orden y no pueden cruzarse en un deadlock.

---

## Alternativas consideradas

### A. Bloqueo optimista (versión en la fila)
Rechazada. En alta contención por la última unidad los reintentos se
multiplican y un reintento puede volver a chocar, entrando en ciclo.

### B. Bloquear solo los artículos, sin bloquear al organizador
Rechazada. Deja abierta la carrera de RN01: dos peticiones del mismo
organizador superan el límite de 5 porque el contador de pendientes no está
protegido por ningún bloqueo.

### C. Bloqueo pesimista con orden ascendente y bloqueo del organizador
Aceptada. Es la decisión descrita arriba.

---

## Sobre el código 409

Con el orden ascendente no se produce ningún deadlock: la segunda petición
espera el bloqueo, lo adquiere, y ve el inventario agotado. Por lo tanto el
409 que recibe es siempre por inventario insuficiente, no por "deadlock
evitado". No existe un código distinto para deadlock; el ordenamiento es una
medida preventiva que evita que ocurra, no un caso de respuesta.

---

## Defensa en profundidad

Además de los bloqueos, PostgreSQL aplica el CHECK
articles_available_units_range, que rechaza available_units fuera del rango
[0, total_units]. Si un defecto de código intentara saltarse el bloqueo, la
base de datos sigue siendo la última defensa.

---

## Estrategia de prueba de concurrencia (ConcurrentRentalTest)

RefreshDatabase no sirve para esta prueba: envuelve cada test en una
transacción que hace rollback, y otra conexión o proceso no vería esos datos
ni sus bloqueos. Por lo tanto:

1. ConcurrentRentalTest usa DatabaseMigrations, de modo que los datos de
   preparación quedan commiteados y son visibles para otros procesos.
2. La prueba lanza dos procesos hijos (Symfony Process) que ejecutan
   POST /api/v1/rentals en paralelo contra el propio contenedor
   (127.0.0.1), que ya sirve nginx y php-fpm cuando las pruebas corren con
   docker compose exec api php artisan test.
3. Se afirma que exactamente una respuesta es 201 y la otra 409, en cualquier
   orden, y que available_units queda en 0.
4. Si el entorno no sirve HTTP, la prueba falla con un mensaje explícito.
   No se marca como saltada en silencio: una prueba de concurrencia que no
   corre no protege nada.

Esta estrategia es el riesgo técnico más grande del backend y se aborda el
15 de noviembre, antes de seguir con controladores.

---

## Consecuencias

- RentalService bloquea primero la fila del organizador y luego los artículos.
- El ordenamiento orderBy('id') es obligatorio, no opcional.
- El 409 significa siempre inventario insuficiente.
- Article::withTrashed() es obligatorio en la consulta de bloqueo.
- ConcurrentRentalTest no usa RefreshDatabase.
- No se agregan componentes fuera del alcance: solo características de
  Laravel y PostgreSQL ya declaradas.
